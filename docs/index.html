PayPay in Eight Weeks

A prep schedule for a Java backend engineer with five years' experience, matched line by line to two PayPay openings in Tokyo: Backend Engineer (Payments) and Backend Engineer (Core Banking System). It's built for one hour on weekdays and two to three hours at the weekend. Week 1 starts whenever you start. Tick weeks off as you finish them, and tick questions once you can answer them out loud. Why eight weeks

現実

Five years of backend work means you already know the job. What PayPay tests is different: timed algorithm problems, crisp answers on theory you rarely say out loud, and a payments design under pressure. Here is where the hours go.

Coding: ~40 problems + 3 mocks + redos34 hrs +Theory: Java, concurrency, DB, cache, security, tuning24 hrs +Payments + core banking design11 hrs +AI workflow, stories + mock interviews11 hrs Needed80 hrs = 8 × 10

Coding gets almost half the hours because the online coding test is a hard filter. Recent candidates had to pass every test on 4 problems, from easy to hard. Five years of production code doesn't make you fast at LeetCode. Only practice does.

Apply in week 5, not week 8. The coding test link usually arrives within 1–2 weeks of applying, and the full loop takes 3–4 weeks. Applying in week 5 puts the coding test around week 7, when your coding is at its sharpest, and the design round after week 7.

Two ways this length changes

  • You already solve LeetCode mediums in under 25 minutes. Merge weeks 1 and 2 into one and apply in week 4. The plan drops to 7 weeks. Test yourself with one timed set before deciding. Most people overestimate their speed.
  • You are running the N3 plan at the same time. 20 hours a week won't survive a bad month. For these 8 weeks, use the N3 plan's own bad-week protocol: keep the 20-minute SRS reviews, pause new chapters, and resume N3 in week 9. Otherwise, stretch this plan to 13 weeks at 6 hours.

並 Java & concurrency

When is an object eligible for GC? How does the GC work?reported
  • An object is eligible once it's unreachable from the GC roots: thread stacks, static fields, JNI references. Reference cycles alone don't keep objects alive.
  • Most objects die young, so the heap is split into generations. The young generation (Eden plus survivor spaces) is collected by copying live objects out. The old generation uses mark and compact.
  • G1 has been the default since JDK 9: region-based, with a pause-time target. ZGC keeps pauses under a millisecond and has been generational since JDK 21. Parallel GC suits batch jobs that need raw throughput.
  • A Java "memory leak" means objects stay reachable: static caches that never evict, ThreadLocal in pooled threads, listeners never unregistered, unbounded queues.
  • Have a production story ready: how you found a leak or long pauses using GC logs, a heap dump (jcmd GC.heap_dump) analysed in Eclipse MAT, or JFR.
JVM memory areas; the JVM inside a containercore
  • Heap (objects), a stack per thread (frames, local variables), Metaspace (class metadata, in native memory), code cache, direct buffers.
  • A Kubernetes memory limit covers all of these, not only the heap. Size the heap with -XX:MaxRAMPercentage=75 instead of a fixed -Xmx, and leave headroom. Otherwise the OOM killer ends the pod with exit code 137.
Race condition vs data race. Deadlock vs livelock vs starvation.reported
  • Data race: two threads access the same memory at the same time, at least one writes, and nothing synchronizes them. Race condition: the result depends on timing, like check-then-act. You can have a race condition without a data race: two individually synchronized calls, if (!map.containsKey(k)) map.put(k, v), still race.
  • Deadlock: threads wait on each other forever. It requires all four Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait. Fix it with a global lock order, or tryLock with a timeout.
  • Livelock: threads keep reacting to each other and stay busy, but nothing progresses. Starvation: a thread never gets the resource, for example because of unfair locks.
  • Payments example: transfers A→B and B→A running at once can deadlock. Always lock the two accounts in ID order.
synchronized vs ReentrantLock vs volatile vs Atomic*core
  • volatile makes every thread see the latest value, but it doesn't make operations atomic: count++ is still broken.
  • AtomicLong uses lock-free compare-and-set. LongAdder scales better for heavily contended counters.
  • ReentrantLock adds tryLock, timeouts, interruptible waiting, fairness and multiple Conditions. Always unlock in finally.
  • A double-checked-locking singleton needs volatile, or another thread can see a half-constructed object.
HashMap internals, and how ConcurrentHashMap differscore
  • An array of buckets; the index is (n-1) & (h ^ h>>>16). The table doubles when it's more than 75% full. A bucket becomes a red-black tree once it holds 8 entries and the table has at least 64 buckets.
  • If a key's hashCode changes after insertion, you can't find it again. Always override equals and hashCode together.
  • ConcurrentHashMap (Java 8+): compare-and-set to fill an empty bucket, otherwise synchronized on the bucket's first node. Reads take no lock. Null keys and values aren't allowed. Use computeIfAbsent and merge for atomic check-and-update.
  • A plain HashMap with concurrent writers loses updates. Before Java 8, a concurrent resize could even create an infinite loop.
Thread pools, sizing, CompletableFuture, virtual threadsreported
  • How ThreadPoolExecutor handles a task: start core threads, then fill the queue, then grow to the max pool size, then reject. Executors.newFixedThreadPool uses an unbounded queue, which can run out of memory under load. Build pools with a bounded queue.
  • Sizing: CPU-bound work needs about one thread per core. IO-bound work needs cores × (1 + wait time / compute time).
  • CompletableFuture: pass your own executor (the default is the shared common pool) and add orTimeout plus exceptionally.
  • Virtual threads (JDK 21) make blocking IO cheap. Don't pool them. Blocking inside synchronized pins the underlying carrier thread; JDK 24 fixed that (JEP 491).
Live coding: write a thread-safe bounded blocking queuecore
class BoundedQueue<T> {
    private final Deque<T> q = new ArrayDeque<>();
    private final int cap;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    BoundedQueue(int cap) { this.cap = cap; }

    void put(T t) throws InterruptedException {
        lock.lock();
        try {
            while (q.size() == cap) notFull.await();   // while, not if: spurious wakeups
            q.addLast(t);
            notEmpty.signal();
        } finally { lock.unlock(); }
    }

    T take() throws InterruptedException {
        lock.lock();
        try {
            while (q.isEmpty()) notEmpty.await();
            T t = q.removeFirst();
            notFull.signal();
            return t;
        } finally { lock.unlock(); }
    }
}
Spring IoC / dependency injection; @Transactional pitfallsreported
  • IoC means the container creates your beans and supplies their dependencies. Prefer constructor injection: fields can be final, it's easy to test, and circular dependencies fail at startup. Beans are singletons by default, so they must be stateless or thread-safe.
  • @Transactional works through a proxy. Calling the method from inside the same class skips the transaction. By default it rolls back only on unchecked exceptions, not checked ones, unless you set rollbackFor.
  • Propagation: REQUIRED (the default) joins the current transaction. REQUIRES_NEW starts a separate one, useful for an audit log that must survive the outer rollback.
  • Never call a bank or partner API inside a database transaction. It holds connections and row locks for the whole network call.
Modern Java: records, sealed types, pattern matching, stream pitfallscore
  • Records work well as immutable DTOs. Sealed interfaces plus pattern-matching switch (JDK 21) force you to handle every case, e.g. PaymentResult = Success | Declined | Pending.
  • String is immutable: safe to share between threads, its hash is cached, and it can be interned in the string pool.
  • parallelStream runs on the shared common pool, so keep it off request paths.
  • PayPay also uses Kotlin and Scala. Know Kotlin's null safety and data classes at a basic level.
Distributed locks, leases and fencing tokenscorePayments
  • A synchronized block protects one JVM. With 30 pods, you need the database, Redis or a coordination service (ZooKeeper, etcd) to decide who holds the lock.
  • Redis lock: SET lock:payout:42 <uuid> NX PX 30000. Release it with a Lua script that deletes the key only if the value is still your UUID, otherwise you could delete someone else's lock.
  • Every distributed lock is really a lease. A long GC pause or network stall can outlast the TTL, and then two holders both believe they own the lock. Fix: a fencing token, a number that goes up with every grant. The resource rejects writes carrying an older token (UPDATE … WHERE last_token < :token).
  • For money, prefer not to need a lock at all: a unique constraint, a conditional UPDATE, or partitioning so a single consumer owns each account. Use a lock to avoid wasted work, not as the only thing keeping data correct.
  • Related vocabulary they may test: clocks can't order events across machines (use logical clocks or database sequences), leader election, split brain, quorum.
Kotlin and Scala for a Java engineer; Java vs C memorycore
  • Kotlin (Payments stack): nullable types (String?) checked at compile time, data class, extension functions, and coroutines, which are lightweight like virtual threads but suspend explicitly with suspend. It interoperates fully with Spring and Java libraries.
  • Scala: immutable collections by default, case class, Option instead of null, Future. You only need to read it, not write it, on day one. The posting asks for the "ability to learn additional coding languages".
  • C (Bank accepts "C or Java"): manual malloc/free, pointers, no bounds checks. Buffer overflows and use-after-free are the bugs Java's GC and bounds checks rule out. Legacy bank systems often run C or COBOL, which is why this matters when modernising them.

基 Networking, Linux & containers

What happens when you open a URL?reported
  • Browser cache, then OS cache, then the DNS resolver works recursively (root → TLD → authoritative server) and may return a CDN or load balancer address.
  • TCP three-way handshake, then a TLS 1.3 handshake in one round trip (key exchange, certificate check). HTTP/3 runs over QUIC on UDP and merges these steps.
  • The HTTP request goes to a load balancer or API gateway (TLS termination, auth, rate limiting), then the service, then the database or cache, and back. Keep-alive reuses the connection.
  • The browser parses HTML, fetches assets and renders. Be ready to go deeper into whichever layer they pick.
TCP vs UDP; HTTP/1.1 vs 2 vs 3; which HTTP methods are idempotentcore
  • TCP: ordered, reliable, with flow and congestion control. UDP: individual packets with no guarantees, used by DNS, video and QUIC.
  • HTTP/2 sends many requests over one TCP connection, but one lost packet still stalls all of them. HTTP/3 over QUIC fixes that.
  • Idempotent methods: GET, PUT, DELETE, HEAD, OPTIONS. POST is not idempotent, which is why payment APIs need an idempotency key.
  • Know when to return 409 (conflict), 422 (valid format, invalid content), 429 (too many requests), 503 and 504.
A Java service is at 100% CPU in production. How do you debug it?reported
  • Check metrics first: did it start with a deploy? Look at traffic, GC time and database latency.
  • Run top -H -p <pid> to find the hottest thread, convert its thread ID to hex, and find the matching nid in a jstack thread dump. Or profile with async-profiler or JFR.
  • Also know: process vs thread, load average (it counts threads waiting on IO), file descriptor limits ("too many open files"), ss -s for connection counts, vmstat, iostat.
What is a container, really? Container vs pod?reported
  • A normal Linux process, isolated with namespaces (pid, network, mount and others) and resource-limited with cgroups, running on a layered image filesystem. Unlike a VM, it shares the host's kernel.
  • A pod is one or more containers sharing a network namespace and volumes. Know liveness vs readiness probes, rolling deploys and autoscaling. PayPay deploys with ArgoCD, where git is the source of truth for what runs.

基 Databases

Explain ACID in detail, using a paymentreported
  • Atomicity: debiting the payer and crediting the merchant both happen or neither does (the undo log makes this possible).
  • Consistency: rules hold before and after every transaction, e.g. balance >= 0 and ledger debits equal credits.
  • Isolation: concurrent transactions don't see each other's half-finished work, up to the configured isolation level.
  • Durability: once committed, data survives a crash (redo log or write-ahead log, fsync, replication).

The anomaly that loses money is the lost update: read the balance, compute in code, write it back. No isolation level fixes that on its own. Use an atomic UPDATE … SET balance = balance - ?, SELECT … FOR UPDATE, or a version column.

Autocommit, COMMIT vs ROLLBACK, savepointsreported
  • With autocommit on (the default in MySQL and JDBC), every statement is its own transaction. START TRANSACTION or setAutoCommit(false) groups statements together.
  • COMMIT makes the changes permanent and releases locks. ROLLBACK undoes them. SAVEPOINT plus ROLLBACK TO undoes only part of a transaction.
  • In MySQL, DDL statements like ALTER TABLE commit the current transaction implicitly.
Optimistic vs pessimistic locking. When do you use which?core
-- pessimistic: hold the row lock until commit (hot rows, short transactions)
SELECT balance FROM wallet WHERE user_id = ? FOR UPDATE;

-- optimistic: detect the conflict and retry (low contention)
UPDATE wallet SET balance = balance - :amt, version = version + 1
 WHERE user_id = :uid AND version = :v AND balance >= :amt;
-- 0 rows updated → conflict or insufficient funds → re-read and decide
Indexes: B+tree, composite, covering, EXPLAINcore
  • InnoDB stores the table itself as a B+tree ordered by primary key. A secondary index stores the primary key, so a lookup reads the index and then the table.
  • A composite index on (user_id, created_at) follows the leftmost-prefix rule. It serves WHERE user_id = ? ORDER BY created_at DESC, exactly the transaction history query.
  • A covering index holds every column the query needs, so the table lookup is skipped. Every index slows writes.
  • For history screens, paginate with a cursor (WHERE created_at < ?) rather than a large OFFSET.
SQL vs NoSQL: which would you use where at a payments company?reported
  • Relational (MySQL, Aurora, TiDB): ledger, balances, orders. Anything needing multi-row transactions and constraints.
  • DynamoDB: key-value access at huge scale with predictable latency: idempotency records, sessions, device tokens. Design the tables around your queries and avoid hot partition keys.
  • Redis: caching, rate limiting, short-lived tokens. Never the source of truth for money.
  • Scaling SQL: read replicas (watch replication lag, and read your own writes from the primary), sharding by user ID, or a distributed SQL database.
Caching patterns and how caches failcore
  • Cache-aside: on a miss, load from the database and fill the cache; on a write, invalidate. Add random jitter to TTLs.
  • Stampede: a hot key expires and thousands of requests hit the database at once. Fix: let one request reload it, or refresh early. Penetration: lookups for keys that don't exist. Fix: cache the "not found" result, or use a Bloom filter. Avalanche: many keys expire at the same moment. Fix: jittered TTLs.

CREATE TABLE account (

  customer_id  BIGINT NOT NULL,
  type         VARCHAR(16) NOT NULL,       -- ORDINARY, TIME_DEPOSIT

  amount       BIGINT NOT NULL,             -- signed: -debit / +credit
  PRIMARY KEY (journal_id, account_id),
  INDEX (account_id, journal_id)            -- statement query
);
  • Talk through the choices: integer yen instead of floats, append-only entries, a unique external reference for idempotency, a value date separate from the booking timestamp (a transfer made at 23:59 on a holiday settles on the next business day), and CHECK constraints so the database enforces the rules too.
  • Migrations run through Flyway, and they must be backward-compatible (expand, then migrate, then contract) because old and new pods run side by side during a rolling deploy.
NoSQL schema design: model it in DynamoDBcorePaymentsBank
  • Start from the access patterns, not the entities. List them first: get a payment by ID, list a user's payments newest first, look up an idempotency key.
  • Single table: PK = USER#123, SK = PAY#2026-09-15T10:00:00#p789 serves the history query with a Query that uses ScanIndexForward=false. A GSI on PK = PAY#p789 serves lookup by ID.
  • Idempotency: PutItem with ConditionExpression attribute_not_exists(PK) plus a TTL attribute so old keys expire. Use TransactWriteItems (up to 100 items) when two writes must happen together.
  • Hot partitions: a merchant with millions of payments per day as a single PK gets throttled. Add a shard suffix (MERCHANT#9#07) and fan out reads across the shards.
  • Consistency: GSIs are eventually consistent, and strongly consistent reads work only on the base table. Know this before claiming DynamoDB for balances.
  • TiDB and Aurora are the other side of the trade: SQL and transactions, scaling out (TiDB) or up with read replicas (Aurora).
Redis as a distributed cache: cluster, eviction, keeping it consistent with the DBcorePayments
  • Redis Cluster splits keys across 16,384 hash slots. A multi-key operation needs all its keys in the same slot, so use hash tags: {user:123}:limits. Replicas are asynchronous, so a failover can lose the latest writes.
  • Eviction: allkeys-lru or allkeys-lfu for a pure cache. noeviction when losing a key would be a bug, e.g. rate-limit counters. Watch memory fragmentation and big keys.
  • Consistency with the database: update the database, then delete the cache key (don't write the new value, or two concurrent writers can leave a stale one). For stronger guarantees, invalidate from change data capture events. Set a TTL anyway as a safety net.
  • Local cache (Caffeine) plus Redis: fastest for reads, but every pod needs invalidation, e.g. via Redis Pub/Sub. Keep local TTLs short.
  • Latency: one slow command like KEYS * blocks the single-threaded event loop for everyone. Use SCAN, pipelines, and connection pools (Lettuce).

基 Distributed systems

CAP / PACELC. Which side should a wallet choose?reported

During a network partition, a system must choose between staying consistent and staying available. PACELC adds that even without a partition, you trade latency against consistency. Balances and the ledger choose consistency: refuse the payment rather than allow a double spend. Transaction history, notifications and points can be eventually consistent.

Monolith vs microservicesreported
  • Microservices give teams independent deploys, independent scaling and fault isolation. The cost: network failures, distributed transactions, harder debugging and more operations work.
  • PayPay itself moved from a monolith to microservices. Bring your own story of splitting a service or a database, e.g. with the strangler pattern.
Kafka: ordering, delivery guarantees, consumer groupscore
  • Order is guaranteed only within one partition. Key messages by paymentId or userId so one entity's events stay in order.
  • Within a consumer group, each partition goes to one consumer, so the partition count caps how many consumers can work in parallel.
  • Committing the offset after processing gives at-least-once delivery, so consumers must handle duplicates (e.g. a table of processed event IDs). Exactly-once exists only inside Kafka, using the idempotent producer and transactions.
  • For messages that keep failing, use a retry topic and a dead-letter topic. Monitor consumer lag.
The dual-write problem, the outbox pattern, saga vs two-phase commitcore
  • If you save to the database and then publish to Kafka, a crash between the two leaves them out of sync. Outbox pattern: insert the event into an outbox table in the same database transaction, then a separate process publishes it (by polling, or change data capture like Debezium).
  • Two-phase commit blocks when its coordinator fails, and banks don't support it anyway.
  • Saga: a chain of local transactions, each with a compensating step. Example: debit the wallet, the bank charge fails, refund the wallet.
Timeouts, retries and circuit breakers (Resilience4j)core
  • Every remote call gets a timeout. Retry only idempotent operations, with exponential backoff and random jitter, and cap the total retries.
  • A circuit breaker is closed (normal), opens after repeated failures (fail fast without calling), then goes half-open to test with a few calls. Bulkheads give each dependency its own thread pool, so one slow service can't use them all.
  • A timeout does not mean the call failed. With a bank, the outcome is unknown: check the status with the bank or reconcile before retrying.
Platform components: a REST API, a Pub/Sub system, a database clientcorePaymentsBank
  • REST API: resource nouns (POST /payments, GET /payments/{id}), an Idempotency-Key header on POST, cursor pagination, versioning in the path or a header, and error bodies with a stable machine-readable code. Declarative clients like Feign generate the caller side, so wrap them with Resilience4j timeouts and retries.
  • Pub/Sub vs queue: Pub/Sub delivers every event to every subscriber group (Kafka topics, SNS). A queue gives each message to one worker (SQS). Designing one yourself means choosing ordering scope (per key), acknowledgement mode, retention, replay, and a dead-letter path.
  • Database client: a connection pool (HikariCP: start around 2× the database's CPU cores, not 200), statement timeouts, retrying only on errors known to be safe (deadlock, serialization failure), read/write routing to replicas, and metrics per query. If you have written a shared library like this, it's the best story for this line of the posting.
Which AWS services would you use for a payments or banking backend, and why?corePaymentsBank
  • Compute: EKS (PayPay uses Kubernetes and ArgoCD). Data: Aurora MySQL (storage copied across 3 AZs; a replica usually takes over in under a minute), DynamoDB, ElastiCache for Redis. Messaging: MSK (Kafka) or SQS/SNS. Security: KMS for encryption keys, Secrets Manager, IAM roles per service account, PrivateLink or VPC endpoints so traffic never touches the internet.
  • Resilience: multi-AZ by default. Multi-region is a cost and consistency decision: active-passive for the ledger, active-active only for stateless or eventually consistent parts.
  • Say why you chose each service, and name one you would not use and why. That's the "middleware selection" skill the Core Banking posting asks for.

基 Production: tuning, security, operations

p99 latency on an API doubled. Walk through tuning it.coreBank
  • Measure before changing anything. Use a trace to find which span grew: the application, the connection pool wait, the database, or a downstream call.
  • Database: slow query log, EXPLAIN ANALYZE, a missing composite index, N+1 queries from JPA lazy loading (fix with a fetch join or batch size), lock waits (performance_schema.data_lock_waits), large OFFSET pagination.
  • Application: an exhausted HikariCP pool shows up as connection is not available, request timed out. Look at GC pauses in the logs, thread dumps for blocked threads, and serialization cost.
  • Load test the fix at the target traffic (Gatling or k6) and compare p50, p99 and p99.9 before and after. Report numbers, not "it felt faster".
Security-conscious development for a financial web appcoreBank
  • OWASP Top 10, with the fix for each: broken access control (check ownership on every request, e.g. GET /accounts/{id} for someone else's ID, known as IDOR), injection (bound parameters only), cryptographic failures (TLS everywhere, KMS-managed keys, PII encrypted at rest), SSRF, vulnerable dependencies (Snyk in CI, which PayPay uses).
  • Authentication: short-lived tokens, step-up authentication for transfers, rate limits and lockouts on login and OTP. Service-to-service: mutual TLS or signed tokens.
  • Data: mask account numbers and personal data in logs, keep an append-only audit log of who changed what, separate duties for production access.
  • Japan-specific: Japanese banks follow the FISC Security Guidelines (from the Center for Financial Industry Information Systems) and the FSA's supervisory guidance. Personal data falls under the APPI. Naming these shows domain awareness. You don't need to recite them.
Monitoring, alerts and failure analysis: what do you page on?corePaymentsBank
  • Three signals: metrics (RED per endpoint: rate, errors, duration; USE per resource), structured logs with a trace ID (PayPay uses ELK and Kibana), and distributed traces.
  • Page on symptoms users feel, tied to an SLO: payment success rate, p99 latency, and money correctness, meaning ledger imbalance, unreconciled bank transactions older than N minutes, and stuck UNKNOWN payments. Send CPU and disk alerts to a ticket, not a page. Alert on how fast the error budget is burning, not on single spikes.
  • Failure analysis: a timeline, the trigger, the root cause (keep asking "why"), what made the impact bigger, then action items with owners. Blameless. A real example worth knowing: in October 2023 the Zengin interbank network failed for about two days after a system update, and transfers between some banks stopped. "The user taps Pay three times." How do you guarantee exactly one charge?reported

Answer with layers. A fix on the client alone is never enough.

  • Client: disable the button, generate one Idempotency-Key (a UUID) per checkout, and send the same key on every retry.
  • Server: an idempotency table with a unique constraint on (user_id, idem_key), storing a hash of the request, its status, and the response.
  • Duplicate arrives while the first is still running: return 409 and let the client poll. If the first already finished, return the saved response. Same key but a different request body: return 422.
  • Business key: a unique merchant_order_id per merchant, so even a buggy client sending new keys can't pay the same order twice.
  • Downstream: send the bank a deterministic ID so its side is idempotent too, and deduplicate Kafka consumers by event ID.
@Transactional
public PaymentResponse pay(PayCommand cmd) {
    try {
        idemRepo.insert(cmd.userId(), cmd.idemKey(), cmd.hash(), Status.IN_PROGRESS); // unique index
    } catch (DuplicateKeyException e) {
        IdemRecord r = idemRepo.find(cmd.userId(), cmd.idemKey());
        if (!r.hash().equals(cmd.hash())) throw new IdempotencyMismatch();     // 422
        if (r.status() == Status.IN_PROGRESS) throw new RequestInProgress();   // 409, client polls
        return r.response();                                                   // replay
    }
    int rows = walletRepo.debit(cmd.userId(), cmd.amount());  // … WHERE balance >= :amt
    if (rows == 0) throw new InsufficientFunds();              // rolls back the idem row too
    Payment p = paymentRepo.save(Payment.captured(cmd));
    ledger.post(p);                                            // debit user, credit merchant
    outbox.add(new PaymentCaptured(p.id()));
    PaymentResponse resp = PaymentResponse.of(p);
    idemRepo.complete(cmd.userId(), cmd.idemKey(), resp);
    return resp;
}

Explain the trade-off: the idempotency row sits in the same transaction, so a crash can't leave anything half done. Flows that call a bank can't work this way. Commit a PENDING state first, call the bank outside the transaction, then update the state.

Payment state machine and the "unknown" bank resultreported
CREATED→PENDING_BANK→SUCCEEDED/FAILED/UNKNOWN→REFUNDED
  • Enforce transitions with a conditional update: UPDATE payment SET status = 'SUCCEEDED' WHERE id = ? AND status = 'PENDING_BANK'. A duplicate webhook then changes nothing.
  • A bank timeout means UNKNOWN, not FAILED. A background job asks the bank for the status, and the daily reconciliation against the bank's settlement file catches anything still open.
  • For top-ups, credit the wallet only after the bank confirms. For payouts, hold the funds first, then finalise.
Why a double-entry ledger instead of just a balance column?core
  • Every money movement is a set of entries that sum to zero, e.g. user wallet −¥1,000 and merchant payable +¥1,000. Entries are append-only: never updated or deleted. A mistake is fixed with a reversing entry.
  • The balance is a cached total of the ledger, updated in the same transaction and regularly checked against it. This gives the audit trail that financial regulators in Japan expect.
  • Store money as long minor units or BigDecimal plus a currency code, never double. Yen has no decimal places.
Campaign spike: "20% cashback for the first 1M payments." How does the system survive?core
  • PayPay is known for huge cashback campaigns, so expect this follow-up.
  • Keep the payment path lean: calculate cashback asynchronously from the PaymentCaptured event, so an overloaded campaign service can't block payments.
  • Budget: an atomic decrement in Redis (a Lua script) as a fast gate, with the database as the source of truth. Accept a small overshoot, or reserve budget in chunks.
  • Token-bucket rate limits per user and merchant, capacity scaled up before launch, shedding non-critical reads, and queueing writes.
Design a core banking system: accounts, transfers, interest, end of daycoreBank
Channels: app, PayPay, ATM→Transfer / posting service→Ledger DB→Zengin gateway→Batch: interest · statements · regulatory reports
  • Posting engine: every transaction becomes a balanced journal with a unique reference. Account-level serialisation (row lock in account-ID order, or one Kafka partition per account) prevents overdrafts.
  • Holds: card authorisations and pending transfers reduce the available balance before the ledger balance changes. Two numbers: ledger balance and available balance.
  • Interest: accrue daily on the end-of-day balance, post it on a schedule, withhold tax on it (20.315% on deposit interest in Japan), and round in the customer's favour or by the documented rule. The batch must be safe to rerun: key each posting by (account, value_date, INTEREST).
  • End of day while staying open 24/7: older systems stopped for batch runs, but modern ones don't. Cut over the business date logically, snapshot balances, and run batches against the snapshot while live postings continue.
  • Reconciliation: internal ledger vs Zengin settlement vs BOJ current account, every day, with every difference explained.
An interbank transfer through Zengin: cut-offs, failures, unknown resultsBankPayments
  • The Zengin system (全銀システム) links Japanese banks for domestic transfers. Since 2018 it has run 24/7 for most retail transfers, alongside the traditional weekday core hours. Banks settle the net amounts with each other through their Bank of Japan accounts (BOJ-NET).
  • Your bank's side: debit the sender and move the funds into a clearing (suspense) account in one transaction, send the message, then finalise or reverse when the result arrives. An incoming transfer to a closed account or a mismatched name gets returned (組戻し), which is a new transaction, never a deletion.
  • Timeouts become UNKNOWN, followed by an inquiry and reconciliation. Once sent, a transfer can't be taken back.
  • Bank-account top-ups for PayPay wallets use the same thinking, which is why this item is tagged for both roles.
Modernise a legacy core banking system without losing reliabilitycoreBank
  • Never a big-bang cutover. Use the strangler fig pattern: put a routing layer in front of the old system and move one capability at a time (balance inquiry first, then statements, then transfers last).
  • Data: stream changes from the old database with change data capture into the new store. Run both in parallel with a daily comparison of balances and journals, and cut over only when there have been zero differences for weeks.
  • Shadow traffic: send real requests to the new service, compare responses, and discard its output. Feature flags route by customer segment: employees first, then 1%, then everyone. Every step has a rollback.
  • Leave some things alone: if the old system handles interest correctly, wrap it behind an API and replace it later. Reliability comes first, and the posting says exactly that.

Rules that make it survive

規律

Eight weeks alongside a full-time job is long enough for discipline to slip somewhere. These rules decide what happens when it does.

The minimum viable day is 20 minutes

On a bad day, answer three questions out loud and stop. That's the designed floor, not failure. A 20-minute day keeps your recall warm; a zero day makes the next one twice as hard to start.

Twenty-five minutes, then read the solution

Being stuck for an hour teaches less than reading a solution at 25 minutes and re-solving it cold three days later. The Sunday redo block exists for exactly this.

Say it out loud, in English

Knowing an answer in your head and saying it clearly to an interviewer are different skills. Every theory block ends with you speaking, and recording yourself counts double.

Your CV is their question list

PayPay interviewers dig into whatever technology you list. For each item on your CV, prepare a two-minute explanation and one production story. If you can't, remove the item.

Bad week: cut theory, keep coding

When a week collapses, keep the daily problem and drop the reading. Coding speed fades fastest, and the coding test comes before anything else in the loop.
